## NOTE
- [locked decision: ado_branch_protection] t-5 counts `matchKind DefaultBranch` scopes as protection, but the locked choice lists the scope forms as "(exact ref or matching prefix)". This widens the decision in the safe direction (it detects more protection), so it isn't a conflict. Still, /dross-verify may read it as a deviation. Consider amending the decision text before execution.
- [behaviour not pinned] On ADO, `SyncBacklog`'s non-YouTrack path (internal/boardsync/backlog.go:449) calls `CreateIssue` with `Milestone: <epic id>`. Through t-12, that makes every milestone backlog/deferred item a requirement-type child of the Epic (Hierarchy-Reverse), not only a Related-linked item. That may be the intent, but no decision states it and t-18's backlog test checks only the Related link.
- [locked decision: state_resolution] The rationale "a flat override still targets one tier" doesn't hold for `complete`. Phase closes and milestone-Epic closes (`issue milestone sync --close` passes "" → "complete", issue.go:225) share that key, so a `state_map.complete` override aimed at phases also drives Epic closes. Stock processes use the same Completed name for both types, so the risk is limited to custom processes. No contract covers an Epic close under an override.
- [coverage depth] `TestEveryBoardCommandUsesAzureBoards` (t-20) samples 6 board commands. It doesn't run `issue quick`, `issue task pull`, `deferred add` or `watch` on ADO. Every board command builds its client through `openBoard` → `forge.NewBoard(boardsync.Config(...))` (issue.go:115), so the sample is enough for c-1. The quick lane's create/close on ADO is never exercised, though.
- [semantics] t-6 reads a Removed item as `State "open"`, while t-12's `ListIssues(State: open)` leaves Removed items out. This is deliberate (Removed is neither done nor inbound), but it means `finalizeCard` will move a task card a human Removed to Done on `phase complete`. That is worth knowing when reading t-18/t-20 logs.
- [duplication] t-2's `AzureBoardsClient.doRaw` re-implements the transport rules of `ship.adoRequest` (internal/ship/azuredevops.go:135): Basic `:`+PAT or Bearer, api-version replacement, no redirects, 203 as sign-in. `CheckADOBaseURL` adds a second ADO base-URL shape check beside `project.ParseAzureDevOpsRemote`. One `doRaw` per backend is the established forge pattern, and forge and ship don't import each other, so this is defensible. But two ADO stacks can now drift, and the plan has no parity test between them.
- [strength] The test contracts are unusually concrete and wire-level. Each names the test that breaks and the exact evidence: `%20` never `%2520`, `$expand=relations` with no `fields` param, TF201036 on a second parent, 200-id `workitemsbatch` limit, 255-rune title cut at a multi-byte boundary, `o''brien` WIQL quoting, `test /rev` before re-parenting. There is almost nothing vague to argue with.
- [strength] The mocked-versus-live split matches locked verify_posture. t-20's fake has a self-test proving it "refuses what ADO refuses". t-21 lists the specific mocked assumptions the live run must check (project-scoped backlogconfiguration, whole-tag CONTAINS, System.Tags replace semantics, rev-test failure status). t-8/t-21 keep the committed record mock-only until a real run passes.
- [strength] No two tasks in the same wave touch the same file, and every shared file is ordered by `depends_on` (forge.go t-2→t-7→t-15; boardsync phase.go/task.go t-16→t-17; hostguard_test.go t-5→t-9). Existing reflection and AST guards are handled in the same commit: not_paths.txt rows in t-1, an AST-readable map literal in t-13, tag-free liverecord structs in t-4, and the NewBoard case-count fixture in t-15.

## Summary
Coverage is complete and no locked decision is contradicted, so nothing blocks. Fix the four missing-file gaps first (t-1's enum tests, the hermetic ADO seam stub, doctor.go for t-11, phase.go's `pullURL` caller): as written, each would turn a task's test gate red or break its build.
