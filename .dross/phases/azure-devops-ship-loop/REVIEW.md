# Plan Review — azure-devops-ship-loop

Reviewed: 2026-10-30
Plan: 17 tasks across 6 waves

## BLOCKING
- [coverage] Part of c-5 cannot be delivered: on azure-devops and bitbucket, answering "proceed" leads nowhere. In t-17's §5, `none`, `pending (queued)` or a pending that still carries a reason at window end, and `ask`, all lead to "ask proceed/stop". t-17's §6 then says "`dross ship ci` must pass, then `dross ship merge`". TestShipPromptMergeGate pins this as "§6 runs `dross ship ci` (pass) immediately before `dross ship merge`" and makes no exception for a proceed the user already approved. A user who answers "proceed" reaches §6. There, `ship ci` returns `none` (exit 4) or `ask` (exit 5) again, and the prompt gives no route to the merge. This hits every Bitbucket repo without Pipelines (c-10's `none`) and every ADO repo with no branch build and no build policy. On GitHub, "proceed without CI" goes on to merge today (ship.md §5). Neither t-4 nor t-11 checks CI, so the dead end comes only from the prompt contract.
    Suggestion: Amend t-17's §6 text and TestShipPromptMergeGate so that a proceed the user approved in §5 for the same watched head still reaches `dross ship merge`. A `fail` verdict, or a head that has moved, should still stop the merge.

## FLAG
- [test-contract] t-4 and t-9 both build the `policy/evaluations?artifactId=vstfs:///CodeReview/CodeReviewId/<projectGUID>/<n>` read. They run in parallel in wave 2 and share no helper. Only t-9 pins the artifactId (TestADOEvaluationArtifactID: `repository.project.id`, escaped once). t-4's contract checks only that the evaluations request "carries the preview api-version". If t-4's mock routes on the path alone, an artifactId built from the project name, or escaped twice, still passes. Against the real API that read returns no blocking evaluation, so every policy-blocked completion turns into a plain error (exit 1). The locked `blocked_completion` decision requires awaiting-merge instead.
    Suggestion: Make t-4's mock assert the artifactId: `vstfs:///CodeReview/CodeReviewId/<repository.project.id>/7`, escaped once. Alternatively, make one task own a shared evaluations-read helper that the other reuses.
- [antipattern/files] t-12's row "refs/heads/phase/x gives HeadRefName phase/x, so watch.SplitPRs classifies it as a ship PR" cannot compile where the plan puts it. internal/watch/prs.go imports internal/ship. Every test in internal/ship is `package ship`, and t-12's only test file reuses that package's unexported ADO mocks. Calling watch.SplitPRs from there is an import cycle. t-7's validator (internal/ship/ado_live_record_test.go) has the same problem with `prtriage.ReplyMarker`: internal/prtriage/items.go imports ship.
    Suggestion: Have t-12's row assert only `HeadRefName == "phase/x"`; t-16's cmd-level TestWatchAzureDevOpsShipPRs already covers the SplitPRs classification end to end. In t-7, match the marker as a literal string, not through prtriage.
- [antipattern/vague-setup] t-7's runbook prerequisites are a scratch repo with `dross init`, a verify pass and a hand-set comment-resolution policy. Three things the 11 steps need are missing:
  (a) A pipeline on the scratch repo, YAML or classic, plus an agent that can run it. The ci step's evidence must include "the build page URL" (t-7), and t-18 requires the verdict to "agree with the build page". A new org may also have no Microsoft-hosted parallelism until its free-grant request is approved. In that case builds sit at notStarted, which gives `pending (queued)` and then ask, and the step never gets a pass.
  (b) An inline comment posted by hand in the ADO UI. dross cannot post one, and the listing step needs one.
  (c) Resolving the reviewer's active thread(s) before the merge step. The runbook's own comment-resolution policy blocks completion while that inline thread is active. The merge step would then exit 2 (ErrMergeBlocked), and merged-status would never read merged. /dross-respond's reject posts a reply thread but resolves nothing.
  Also, "agrees with the build page" in t-18's contract is not something the validator can check mechanically.
    Suggestion: Add (a)–(c) to the template's runbook comments in t-7. Reword t-18's ci evidence rule to what t-7's validator actually checks: the verdict recorded verbatim plus a build URL on the real host.

The t-4 artifactId pin, t-12's import cycle and the live-runbook prerequisites should be fixed in the same pass.
