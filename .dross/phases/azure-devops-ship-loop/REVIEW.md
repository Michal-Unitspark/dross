# Plan Review — azure-devops-ship-loop

Reviewed: 2026-10-30
Plan: 18 tasks across 6 waves

## BLOCKING
- [locked-decision] `blocked_completion` says a completion blocked by required reviewers, comment resolution or work-item linking "is surfaced and ship holds at awaiting-merge". In the plan, the only route to `ErrMergeBlocked` (and so to t-15's blocked exit code and t-17's "blocked exit -> §7 awaiting-merge") is t-4's `mergeStatus rejectedByPolicy` row. The same t-4 contract sends "a PATCH 400/409" to a generic error with 0 polls, and sends "polls exhausted while active" to a generic `completion not confirmed` error. t-15 maps both to exit 1, and t-17 treats exit 1 as "other non-zero surfaced", not awaiting-merge. ADO normally rejects a policy-blocked completion at the PATCH with a TF401027-style message ("You need at least N approving reviewer(s)…"), or accepts it and leaves the PR active. `rejectedByPolicy` is the merge-result status (push-policy class), and nothing ties it to these three policies. So the three policies the decision names can never reach awaiting-merge, and no t-4 test row covers "required reviewers not approved -> ErrMergeBlocked". Bitbucket has the same gap: t-11's "400 (merge checks)" is a plain error.
    Suggestion: Give t-4 a contract row that sends a blocked completion to `ErrMergeBlocked`. That covers a PATCH refusal naming an unmet policy, and a PR still active once polling ends while a blocking non-CI evaluation is unmet. A per-PR policy-evaluation read is enough to detect it, and the `ci_source` decision already permits that read. Confirm the real wire shape in t-18's comment-resolution probe. Either add the same mapping for Bitbucket's merge-check 400 in t-11, or state that `blocked_completion` is ADO-only.

## FLAG
- [antipattern/files] t-5 makes `bbRequest` "a thin wrapper" over `bbDo` but also says "bbRequest's existing sinks row still holds". Three existing audits say otherwise:
  (a) `TestScreenPrecedesRequestInEveryScreenedTransport` (internal/cmd/secretscan_transport_enum_test.go) fails a Screened row whose function has no request primitive ("one side is missing"). Once `bbRequest` only calls `bbDo`, that is `bbRequest`.
  (b) `TestShipHelpersScrubAtSource` reports `scrubbing helper "bbRequest" was not found reading a body — the list is stale` once `bbRequest` no longer calls `io.ReadAll`.
  (c) Dropping `bbRequest` from `scrubbingHelpers` then fails `TestEveryShipBodyInterpolationRedacts` at every `string(rb)` in the bitbucket callers.
  The contract line "TestScreenPrecedesRequestInEveryScreenedTransport … fail naming bbDo" is also wrong: that test only iterates registered entries. `TestEveryOutboundSeamIsRegistered` is the one that names an undeclared `bbDo`.
    Suggestion: Pick one design and make the contract match it. Either `bbRequest` keeps its own request (not a wrapper), or the audits learn a "wrapper of a screened/scrubbing helper" notion. In the second case, add internal/cmd/secretscan_transport_enum_test.go and possibly internal/secretscan's Transport model to t-5's files.
- [antipattern/files] t-18's contract promises validator behaviour that no task builds. Rows 3–4 say "the validator rejects it unless its evidence shows" the dedupe line, an inline comment with line > 0, ID equality, `git ls-remote` output and merged-status. Row 1 relies on a `partial` posture. t-7's validator only knows `live` / `mock-only`, real-host evidence and the 11 step keys. t-18's files do not include internal/ship/ado_live_record_test.go, so it cannot add the rules.
    Suggestion: Either move the per-leg evidence rules and the `partial` posture into t-7's contract, or add ado_live_record_test.go to t-18's files.
- [test-contract] Stale-head handling loses its message. t-9 (and t-10 for Bitbucket) return `pending` with a Reason naming both SHAs and `dross ship <id>` when the PR head is not the watched SHA. t-15 prints Reason only for `ask`; `pending` prints just `queued|running`. `CIResult.Queued` is unspecified for this case. If it is false, t-17's §5 ("pending -> keep polling", window applies only to none/queued) polls indefinitely and never shows the remedy. The `ci_source` decision's Pending is "running, or queued inside the window", which does not include stale-head.
    Suggestion: Pin `Queued` (or the verdict) for the stale-head case in t-9/t-10. Make t-15 print Reason whenever it is set, or add a contract row showing that the stale-head remedy reaches stdout.
- [test-contract] The merge-blocked exit code is not pinned. t-15 gives `ErrMergeBlocked` "its own code (not 0, not 1)" with no number. t-17's `TestShipPromptCIExitCodesMatch` cross-checks only `ship ci`'s codes. `TestShipPromptMergeGate` checks the wording "maps the blocked exit to awaiting-merge" but not that the number in ship.md equals the binary's constant. That is the prompt/binary drift the ci test exists to prevent.
    Suggestion: Extend the exit-code-match test to `ship merge`'s blocked code, or pin the number in t-15's contract.
- [test-contract] c-1 requires each comment to carry "the author's id and unique name". None of t-1's eight contract rows asserts `CommentAuthor.Login` == `author.uniqueName`; they cover IDs, noise, anchors, partial lists, Bot class, URL and identity. The Login is what prtriage prints as `@login` and records as the resolution Author. Relatedly, t-1's `AuthenticatedUser` Login falls back to `providerDisplayName`, which is not a unique name (c-3 says "id + unique name").
    Suggestion: Add a row to TestADOThreadInlineAnchor or a sibling test asserting Login == uniqueName, and decide whether the identity fallback should be an error instead.
- [test-contract] c-5 requires a fail verdict "with a link to the failing build". t-9 pins the link only for a rejected build-validation evaluation (`_build/results?buildId=<context.buildId>`). A rejected Status-check policy evaluation (cbdc66da) has no buildId, and no task reads PR statuses for a targetUrl. Its `CIResult.Link` is unspecified and may be empty, so t-15 would print `ci: fail - ` with nothing after it.
    Suggestion: State in t-9 what Link a rejected Status-policy evaluation yields (e.g. the PR URL), with a contract row for it.
- [antipattern/vague-setup] t-18 never says where the live run happens. This repo's `[remote]` is GitHub (project.toml). `dross ship` refuses without a fresh verify pass on a `phase/<id>` branch (ship.md §4 step 1). The live loop therefore needs a scratch ADO repo with a dross project, a phase and a verify record. Neither t-7's runbook description nor t-18 mentions that setup, or where the comment-resolution policy is configured.
    Suggestion: Name the scratch-repo prerequisites (init, phase, verify pass, branch policy) in t-7's runbook contents or in t-18's description, so the pair session does not stall at the first `dross ship`.

## NOTE
- [strength] The test contracts are specific throughout. Each row has the form "if X breaks, TestY fails" with concrete inputs and outputs and request counts ("0 PATCHes", "0 hits", "exactly one POST"). That turns fail-closed behaviour (never a partial list, never `none` on a failed read, full page = error) into assertions, not prose. The permutation row in t-3 ("same verdict under every permutation") is a good guard against order-dependent precedence.
- [strength] The layering is clean. The pure rollup (t-3, no I/O) is split from the fetch (t-9), dispatch (t-13), CLI (t-15) and prompt (t-17), and t-12 reuses `adoCIForPR`, so watch and `ship ci` share one verdict path (c-8). There are seven independent wave-1 tasks, and no two tasks in any wave share a file.
- [strength] The plan matches the real code. Every existing symbol it names exists where it says: `adoRequest`, `adoConn`, `scrubbingHelpers`, `enumScanSites`, `TestAzureDeferredSurfacesFailClosed`, `TestShipRefusesOffAllowlistAPIBase`, `newADOShipMock`, `guardOpenPRsTargeting`, `adoThreadStatus`, `prThreadMaxPages`, `gitRefArgs`, and the ship.md forbidden-switch test (`deletesourcebranch` already banned). It also correctly notes that `mirrorAuthServer` is test-only in package ship, unreachable from cmd. Every new file is created by an earlier or the same task.
- [coverage] All 11 criteria are covered: c-1..c-4 by t-1/t-2 + t-8 + t-14; c-5/c-6/c-10/c-11 by impl + t-13 + t-15 + t-17; c-7 by t-7 + t-18; c-8 by t-12 + t-16; c-9 by t-6. The deferred items (GitHub/GitLab/Forgejo recipes, Bitbucket dependents, other-provider watch and review recipes) are explicitly left alone and guarded by regression rows.
- [rules] r-01 is honoured: every task that edits assets/prompts (t-6, t-16, t-17) runs `make install`, and t-18 starts from `make install`. runtime.mode is native, so there is no tooling conflict. There is no global rules.toml.
- [wave-order] All dependencies are real. t-18's dependencies on t-14 and t-16 are not strictly required by c-7's steps (watch is not one of them), but t-17 already forces wave 6, so no parallelism is lost.
- [test-contract] t-12 turns `ListOpenPRs`' `!= "github"` check into a provider dispatch but, unlike t-8 and t-13, has no padded-provider (`' Azure-DevOps '`) row and no `enumScanSites` registration. Low risk, because the existing check already goes through `configenum.Normalize`.

## Summary
The plan is thorough and grounded in the real code. Before execution it needs four fixes: route a policy-blocked ADO completion to awaiting-merge as the locked `blocked_completion` decision requires; reconcile t-5's thin-wrapper design with the existing transport and scrub audits; add t-18's promised validator rules (and its `partial` posture) to a task that owns the validator file; and make the stale-head `pending` Reason reach the user.
